# 访问模式驱动的机器人训练数据物理布局

## 核心洞察

> 机器人 episode 的逻辑 schema 应保持细粒度和可解释，但底层文件、chunk、GOP 与 cache page 的物理边界，应由训练 sampler 的共同访问模式决定，而不是机械地按 topic 名称或模态类别划分。

训练样本本质上是一类稳定重复的查询。优化数据格式时，真正需要建模的是：哪些字段总被一起读取、读取多长的时间窗口、访问是稀疏还是连续、每次读取跨越多少压缩和网络请求单元。

因此，数据格式不是独立于模型的静态容器。模型的 observation horizon、action chunk、camera sampling、随机采样方式和缓存层级都会反过来决定最优物理布局。

## 从训练查询反推物理布局

| 访问模式 | 更合适的物理设计 | 主要风险 |
|---|---|---|
| 多路相机总是同步读取 | 相机按时间交错写入同一访问组 | 只读单路相机时产生组内读放大 |
| state 与 action 总是读取同一稠密窗口 | 放入同一 time-major chunk stream | 只做 state-only 分析时会携带 action |
| 视频读取长而连续 | H.264 与较大 GOP，可摊薄关键帧 seek | 任意帧随机访问成本上升 |
| 视频只取少量稀疏帧 | 更短 GOP、独立帧编码或解码缓存 | 压缩率下降、容量和带宽上升 |
| 训练前先按质量、任务和版本筛选 | 把筛选字段放入独立列式 manifest | manifest 与原始 episode 版本可能漂移 |
| 对象存储或远端文件系统读取 | chunk 对齐 range read 与缓存页，减少请求数 | chunk 过大会增加无关字节和解压成本 |

这里的关键变量不是 topic 数量，而是**共同访问组数量**。若一份样本固定访问两组数据，增加组内 topic 不应线性增加网络往返；但这只有在组内 topic 确实共同访问时才成立。

## Dyna-2 的实例

[[ResearchSources/Sources/Training Dyna-2 at million-hour scale, repeatably|Dyna-2 infrastructure]] 把 episode 从 H5 单帧 JPEG 迁移到 MCAP，并组合了两个正交优化：

1. **H.264 与较大 GOP**：利用跨帧压缩降低视频体积；其适用性取决于训练读取的是连续序列还是稀疏帧。
2. **Topic-group chunking**：将 cameras 与 state/action 分成互不共享 chunk 的两条 time-major stream，使请求数随访问组而不是 topic 数增长。

文章 Figure 3 报告：

| 指标 | MCAP+H.264 per-topic | Topic-group | 变化 |
|---|---:|---:|---:|
| 存储体积 | 25.1 MB/相机分钟 | 25.1 MB/相机分钟 | 不变 |
| 样本读取延迟 | 27.0 ms | 9.4 ms | 约 2.9× 更快 |
| Chunk fetch | 11.33 次/样本 | 3.29 次/样本 | 约少 3.4× |

JPEG 单帧基线为 80.3 MB/相机分钟，因此约 68% 的容量下降应归因于 H.264，而不是 topic-group chunking。这个拆分说明：**编码压缩优化字节数，物理分组优化读放大、请求和解压次数，两者必须分别消融。**

## 可迁移的设计原则

### 1. 先记录访问 trace，再设计分组

从真实训练 dataloader 记录每个 sample 读取的 topic、时间区间、字节范围与 cache hit。由共同访问矩阵聚类，比“所有 camera 一组、所有 state 一组”的固定规则更可靠。

### 2. 同时优化三种放大

- **字节放大**：取一个样本实际读回多少无关字节；
- **请求放大**：一个样本触发多少次文件打开、range request 或 chunk fetch；
- **解码放大**：为得到目标帧需要解压多少 chunk、从关键帧向前解码多少帧。

只优化其中一个指标可能把瓶颈推到另一个层级。例如 per-topic chunk 减少字节放大，却可能让请求数随 topic 线性增长；大 GOP 降低容量，却可能显著增加随机帧解码。

### 3. 冷缓存与热缓存必须分开测

本地 NVMe、page cache、分布式缓存与对象存储的最优 chunk 大小并不相同。应至少分别报告 cold/warm cache 下的：

- bytes/sample 与 chunk fetches/sample；
- dataloader p50、p95、p99；
- CPU 解码时间与 worker 利用率；
- GPU 等待数据时间；
- cache resident bytes 与命中率。

### 4. 原始归档格式与训练派生格式可以不同

一个自包含、易回放的 episode container 不必同时承担所有训练优化。可以保留不可变的高保真来源，再按具体 sampler 物化训练派生布局；这样能让物理优化随模型改变，而不破坏原始数据的可追溯性。

## 证据边界与反例风险

> [!warning] 第一方工程证据
> Dyna 的数值属于 `author-statement`，没有公开 writer 实现、chunk size/duration、GOP 长度、样本量、对象存储环境、误差条含义或独立复现，因此只能支持设计方向，不能直接外推收益幅度。

- 正文和 Figure 2 图注称 MCAP 默认将多 topic 混入共享 chunk，但 Figure 2 图内又写“Default: one chunk per topic”，Figure 3 的对照也标为 `MCAP+H.264 (per-topic)`。因此最保守的解释是：2.9× 与 3.4× 来自其 per-topic 基线，不能无条件表述为“相对标准 MCAP”。
- “相机总在同一组”不是普遍规律。若训练频繁只取某一路 camera，这种布局会重新引入读放大。
- World Action Model 的长连续视频读取可以摊薄大 GOP seek；稀疏取帧的 VLA 可能得到相反结论。
- 当数据完全驻留本地内存或请求被批量合并时，网络往返不再主导，topic-group 的收益可能明显缩小。

## 建议验证实验

固定同一批 episode、同一 reader 与同一 sampler，对比：

1. 当前布局；
2. 每 topic 独立 chunk；
3. 按共同访问模式分组；
4. 不同 GOP 与 chunk 时间跨度的组合。

实验应同时覆盖对象存储、本地 NVMe、cold cache 和 warm cache，并报告有限样本数、误差分布和尾延迟。只有当 GPU data-wait 同步下降，才能说明存储优化真正改善了训练吞吐，而不是只改善了孤立的 reader microbenchmark。
